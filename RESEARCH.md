# Research and implementation boundary

Passive sources inspected on 2026-10-18 before implementation. This is an independent C++ implementation; Python networking and exploitation code are not imported. Separate experimental builds added on 2026-10-19 implement a bounded WPS exchange, with an explicit uncalibrated result boundary.

## Exact passive signatures

| Evidence key | Source and implemented condition | Scope of inference |
| --- | --- | --- |
| `broadcom_proprietary_ie` | Vendor IE ID 221, **payload length exactly 9**, first four payload bytes `00 10 18 02` | Broadcom component evidence; a driver can emit this while userspace WPS is unrelated |
| `broadcom_fixed_wps_uuid` | Vendor IE prefix `00 50 F2 04`; WPS big-endian TLV type `0x1047` (UUID-E) or `0x1048` (UUID-R), length exactly 16 and value `000102030405060708090a0b0c0d0ebb` | Characteristic advertised WPS identity; no proof of a vulnerable code path |
| `broadcom_wps_identity_defaults` | At least two **distinct fields** match: Manufacturer `Broadcom`; Model Name `Broadcom` or `BroadcomAP`; Model Number `1234` or `123456`; Device Name `BroadcomAP` | Default-identity fingerprint; no active implementation test |

Text comparisons ignore ASCII case, remove trailing NUL bytes and trim surrounding ASCII whitespace. Exact matches only; a longer value beginning with a default string is not a match. The manufacturer, model, device, model number and serial fields use WPS types `0x1021`, `0x1023`, `0x1011`, `0x1024`, `0x1042`. Serial is exported, not a signature. Unknown attributes are length-checked and skipped.

The upstream default-identity test counts fields, not attribute repetitions. C++ follows that rule. Different fields can also accumulate across complete advertisements for the same BSSID. `identity_default_field_mask` records manufacturer=1, model=2, model number=4, device=8. Every evidence key retains a distinct source description in JSON. No BSSID OUI matching is used.

## Parsing and intentional differences

- Accept raw 802.11 management subtypes 8 and 5 only. The fixed header/body needs 36 bytes: 24-byte MAC header, timestamp, beacon interval and little-endian capability flags. BSSID comes from address 3. A zero/multicast BSSID is rejected. No client identity fallback is used.
- Frame version/type checks are explicit. DS/protected/ordered/fragmented management frames are not interpreted. Sequence/retry announcements otherwise aggregate by BSSID. Advertisements with no SSID IE are incomplete; an SSID IE with zero payload is valid hidden identity. Binary SSIDs remain raw bytes.
- Every IE and TLV read checks remaining bytes before advancing. Offsets use subtraction-based bounds checks. An attributable malformed advertisement is retained for an inconclusive entry, but contributes no signature or WPS identity. This is deliberately stricter than upstream's partial attribute salvage and prevents a truncated frame from creating positive evidence or an unsupported negative result.
- Multiple WPS vendor IEs in one advertisement are concatenated in order within a 1024-byte cap before TLV parsing. This supports attribute splits across IEs. UUID attributes with a length other than 16, incomplete headers/values, oversized reassembly and empty WPS payloads are incomplete data.
- Complete unknown IEs are represented by an IE-ID bitset. At most eight vendor prefix/length summaries are retained per AP; overflow is explicit. Full raw IEs are available in the optional bounded PCAP snapshot. Raw payloads are never treated as unbounded C strings.
- Nonempty WPS values aggregate by completeness and retained length; evidence and characteristic field masks are unions. A later missing WPS IE cannot negate prior evidence. No negative result is represented as a statement that a network is safe.

## Default passive builds and experimental WPS probe

The original scanner has additional logic to distinguish WPS implementations by generated protocol exchanges. Its active assessments cannot be derived from a Beacon. Default builds remain passive. The `cardputer_adv_probe` and `cardputer_probe` builds opt into a separate manual session using the stock public driver APIs. Separate `*_transport` builds add a SHA-pinned build-local compatibility wrapper and stop at WSC Start, without a differential. The 1.0.7 `*_fingerprint` builds reuse that compatibility layer with `RADAR_TRANSPORT_ONLY=0` to continue to the bounded first fragment.

The experimental exchange was checked against [`broadcom_fingerprint.py` at 8631a2cf07146568c5634aa6fcee116162883cb1](https://github.com/qkaiser/broadcom-wps/blob/8631a2cf07146568c5634aa6fcee116162883cb1/broadcom_fingerprint.py), downloaded on 2026-10-19 (SHA-256 `be584da942f323aa204e3d8e2e13b5b5c2e6262f91633a3ddc97ab0d7054d447`). It follows `decide_assessment()` and `fingerprint_target()`: an explicit EAP Failure or reason-0 deauthentication after accepted differential TX maps to a Broadcom-like candidate, and a WSC Fragment ACK to a hostapd-like candidate. The upstream README describes the opposite mapping; this discrepancy and absence of real-device calibration are recorded rather than treating either candidate as a patch verdict.

The independent bounded implementation pins BSSID/station/channel, revalidates a fresh complete WPS advertisement, attempts authentication/association and EAP entry, and submits one zero-length first fragment without a continuation. Replies predating the last accepted TX, foreign addresses, encrypted data, non-EAPOL payloads, invalid lengths and MAC fragments are excluded. Cleanup addresses only its own station. The trace is limited to 16 records of 512 captured bytes and distinguishes received frames from TX buffers accepted by the driver; a rejected submission is never represented as a transmitted PCAP record. Verdict-bearing trace overflow becomes UNKNOWN. There is no credential completion or exploit verification.

The installed ESP-IDF 4.4.7 `esp_wifi.h` and [public raw-TX documentation](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-reference/network/esp_wifi.html#_CPPv417esp_wifi_80211_tx16wifi_interface_tPKvib) list beacon/probe/action and non-QoS data support, not raw authentication/association/deauthentication. Stock-driver rejection at authentication is therefore an expected possible outcome, represented as UNKNOWN with its numeric driver error. The stock public-API build remains unsupported for those subtypes. The 1.0.6 compatible device traces establish session replies through WSC Start; implementation-family candidates remain uncalibrated. Host tests simulate both response families, driver rejection, malformed/old responses, cancellation, timeout, trace overflow, export faults and restoration of running/paused scan modes.

Device evidence collected on 2026-10-19 from firmware 1.0.5 contains nine report pairs representing five distinct attempts: two rejected authentication submissions (`ESP_ERR_INVALID_ARG`, 0x102), three revalidation timeouts. No attempt entered the differential. Weak RSSI was observed but does not establish the cause of those timeouts.

The 1.0.6 transport-only experiment pins `libnet80211.a` SHA-256 `6aae206c85e9009a24cd1f28ce535e2a2d578d9687fe2dc77d4697d45ebc8d0f` and `ieee80211_output.o` SHA-256 `d45eb112858cebda77262402b7436db5aa8313df06e28fc78c2e6f40891d9574`. The four-argument sanity-check ABI, original function entry at section offset `0x5c`, lock release on both return paths, and the final linked call path were inspected in the actual Xtensa object/ELF. A build-local copy weakens that symbol and adds an alias; no instruction bytes or global SDK files are changed. The strong wrapper invokes the original check and extends only its invalid-argument result for the exact current generated management request during an explicitly started transport session. Data-frame checks remain stock. The build fails on changed SDK hashes, a wrong linked call target, or a transport image larger than 1 MiB.

Diagnostics now retain a 10-second revalidation window, categorized rejected observations, last-target time/RSSI, AP status/reason, a bounded TX-attempt journal, capture drops and separate API-restoration/observed-RX results. Stock public API reports cannot observe the internal sanity return independently, so that field is null. Transport-only success means receiving WSC Start and queues own-session cleanup immediately, with candidate UNKNOWN. An independent capture on a known control AP must establish actual AUTH/ASSOC/EAP/WSC transport, cleanup and resumed reception. The compatibility strategy is bounded to one investigation cycle of the next blocker; further binary hacks, unstable state or slot overflow stop this approach. A custom native WPS component remains a fallback, requiring AP pinning, custom callbacks, suppressed automatic enrollment and a new flash-size measurement. It is not implemented here.

Additional device evidence collected on 2026-10-19 from firmware 1.0.6 contains nine saved transport reports representing seven distinct attempts. KoBa22626, TP-Link_AE52 and dom each completed AUTH/ASSOC/EAP/WSC entry with captured successful AP replies. Four other dom attempts observed no matching advertisement within ten seconds. Every distinct attempt restored scanner settings and observed a subsequent advertisement; queue/oversize/trace drop counters were zero. These are on-device RX traces, not an independent monitor capture. Cleanup TX was driver-accepted but not independently observed over the air.

Version 1.0.7 retains the transport-only `-C` baseline and adds the explicit `-F` compatibility fingerprint. It sends the same single empty first fragment as the upstream orchestration and never sends a continuation. Only an explicit response after accepted differential TX can produce a family candidate; reason-0 deauthentication before that point, disassociation, other reason codes, stale/unrelated packets and TX rejection cannot do so. Reports identify the actual response and whether the differential was accepted by the driver. A repeated WSC Start does not cause another fragment submission. Native integration tests cover all three classified responses and failure paths, while independent JSON/PCAP decoding checks the exact single-fragment trace. Known implementation calibration remains outstanding.

Version 1.0.7 device exports collected on 2026-10-19 contain eleven distinct attempts: four explicit WSC Fragment ACK responses, one matching EAP Failure, and six timeouts before differential submission. Independent PCAP decoding confirms each classification response follows the one driver-accepted empty first fragment. All attempts restored capture and observed a subsequent advertisement, with zero queue/oversize/trace drops. These are behavior-family candidates rather than independently verified process identities.

The reported T/Enter return-to-list behavior was reproduced in the native UI on a Broadcom-signature AP without WPS. Actual `brcm-018` preserves the plus sign in `HK_Omni_20+_Setup_3a4` as byte 0x2b but contains no WPS vendor IE; `brcm-025` and `brcm-026` contain empty SSIDs and no WPS IE. Version 1.0.8 shares the start-eligibility check between UI and request, retains unavailable confirmation with a precise reason, and refreshes the selected BSSID from live observations before submission. It preserves the existing eligibility limits and creates no transmission or test report for a rejected start. Regression tests cover blocked Enter, hidden SSIDs, a literal plus sign and WPS evidence arriving during confirmation.

The passive classification remains a direct function of complete observations and the three evidence bits. `BROADCOM_SIGNATURE` takes precedence; otherwise complete WPS observations give `WPS_ONLY`, a complete ad without evidence gives `NO_SIGNATURE`, and only incomplete observations give `INSUFFICIENT_DATA`. Malformed later observations do not downgrade earlier complete evidence. Version 1.0.9 splits the visible Broadcom group into `BRCM+WPS` and `BRCM`, placing APs with both observations first. This is a display/sort distinction only: the classification schema, Broadcom count, archive criteria and experimental start requirements retain their meaning. It does not establish an affected WPS service or patch status. Experimental results are kept in separate `test-NNN.json/pcap` reports and do not replace passive evidence.

Version 1.0.10 adds reversible `ALL`/`WPS`/`B+W` display filters. Candidate membership shares the manual test target-eligibility function; it does not start a session or alter passive classification, collection, automatic archives or manual exports. Navigation is bounded by the visible index count. UI regression checks cover unsupported/hidden/incomplete targets, empty results, selection preservation as observations arrive, filter cycling and hidden records retained in exports.

## ESP-IDF behavior and capture path

The matching API documents describe `esp_wifi_start()` as creating/starting the STA control block and `esp_wifi_connect()` as initiating connection. The default active scan behavior belongs to `esp_wifi_scan_start()`, which is not used. Radar registers no connect/reconnect handler, creates no default station netif, does not load credential NVS, and uses an empty station configuration in RAM. There is no Arduino WiFi wrapper or active networking layer.

Country is applied with the SDK's validated `esp_wifi_set_country_code(country, false)` and checked through `esp_wifi_get_country()`. Automatic country adoption is disabled. The source uses `esp_wifi_set_promiscuous_rx_cb`, a management-only `esp_wifi_set_promiscuous_filter`, `esp_wifi_set_promiscuous`, and manual `esp_wifi_set_channel`. A 400 ms timer advances only while running in hopping mode.

In the installed SDK, `wifi_pkt_rx_ctrl_t.sig_len` is explicitly documented as including FCS. Four bytes are removed from accepted frames. Only copied bytes and primitive RX metadata cross the callback boundary through a statically allocated FreeRTOS queue. No parser, display, storage call, blocking wait or large allocation occurs in the callback. Parser stack scratch is bounded at 1024 bytes and runs outside the Wi-Fi task.

The source API audit and mock integration tests verify the application's passive call paths. Espressif radio/driver internals are closed binary code in this toolchain; absence of all RF transmission is not established by host tests. The physical acceptance check is an independent monitor-mode capture. No claim of that measurement is made.

## Hardware and Launcher constraints

The explicit ADV reader uses the official TCA8418 implementation; the original uses the official GPIO matrix implementation. M5Cardputer's automatic keyboard initialization is bypassed, avoiding initialization of the wrong matrix on ADV. The display and M5Unified internal I2C pin map still use board detection with the matching fallback. SD and display use separate SPI hosts. No PSRAM is assumed.

The current upstream Launcher board supports both devices. Its base 8 MB CSV reserves a protected `app0` test partition for Launcher and current code dynamically manages installed OTA apps. Radar packages a normal application image and does not ship or install a partition table. A conservative 1.5 MiB build guard and per-image aligned-size manifest provide an upper bound; the actual installed OTA slot must independently fit the image. `check_launcher_partition.py` performs a read-only check against a supplied actual table. A read-only Launcher API check on the development ADV on 2026-10-19 found the existing Radar slot `brcmrd` at 1,048,576 bytes; all 1.0.7 images require that aligned size. Uploading the ADV image to SD did not modify that table.

## Validation boundary

Host tests compile the production parsers, detector, AP store, scanner, UI, serializers and exporter under address/undefined-behavior sanitizers. Hardware mocks cover callback ownership, bounded queue overflow, channel timing/policy, pause/resume, navigation/export, absent SD, failed/removed SD, write/rename faults and existing-file preservation. Synthetic fixtures cover the three Broadcom signatures independently, ordinary WPS, no WPS, UUID-E/R, identical SSIDs on different BSSIDs, empty/binary SSIDs, duplicate fields, split WPS IEs, malformed lengths and 50,000 deterministic random inputs. Coverage-guided fuzzing runs separately.

PCAP serialization is verified with an independent binary decoder and libpcap/tcpdump: link type 105, classic PCAP, lengths/timestamps and raw management frames. No RadioTap header is synthesized. On 2026-10-18 the device owner reported that 1.0.1 works on Cardputer ADV after the display update. Wireshark GUI, original Cardputer operation and detailed hardware acceptance tests remain unperformed. Compilation, mocks and the basic ADV report do not establish radio sensitivity, regulatory behavior in hardware, battery accuracy, worst-case SD latency, absence of watchdog resets, long-duration heap stability or recovery on the installed bootloader.
